# PaddleOCR 路线实测复盘与后续路线决策

> 状态：**PaddleOCR 路线宣告暂时失败**（代码保留不回撤）。本文记录全部实测数据、问题根源与可行替代路线。
> 测试设备：Redmi Note 13 Pro（骁龙 7s Gen 2 / Adreno 710 / 8 核），Android，竖屏锁定，Flutter + vendored fast_paddle_ocr（PP-OCRv5 mobile + ncnn 20260113）。

## 一、结论（TL;DR）

PaddleOCR 的失败不是单点 bug，而是**架构性不适配**：

> **通用两阶段 OCR（全帧检测 → 逐框识别）× 固定分辨率全帧扫描 × 无帧间连续性的流水线，与"手持移动中识别小尺寸结构化数字码"这一场景根本冲突。**

三条硬性数据判死刑：

1. **单帧预算数学上不成立**：25fps = 40ms/帧预算。实测 det 33ms + rec 40ms/框，1 个文字框就要 73ms（13fps），4 个框 190ms（5fps）。两阶段串行架构下识别成本 = O(框数)，永远跑不满相机帧率。
2. **硬件加速反向优化**：GPU(Vulkan) 上 rec 反而劣化 4 倍（170ms/框 vs CPU 40ms/框），且每次冷启动着色器编译 19 秒；NPU(Hexagon) ncnn 架构上不支持。
3. **准确率触及物理天花板**：相机写死 640×480 时货架标签只有十几像素高，rec 只能瞎猜（实测 `23-6-1234` 被读成 `1|110`）；提到 720p 后手持稍远距离仍不可用（用户实测）。

补充观察：

- 渲染 fps 波动部分源于帧到达的突发性（批处理/掉帧后补发），移动平均口径仅供参考趋势。
- GPU 识别出的垃圾文本置信度低 → 智能继承机制（IoU≥0.45 且 rprob≥0.75 才跳过重识别）永不触发 → 每趟全量重识别 → rec 恒定在 500ms。**准确度不修，任何调度优化都会被低置信度击穿。**
- ncnn 线程配置：det 2 线程 / rec 4 线程（8 核可用 7），CPU 推理本身已与渲染/UI 存在核间竞争。

## 三、问题清单与根源分析

### 3.1 遇到文字延迟飙升（500ms）

**因果链**：rec 串行逐框识别（40ms/框，成本随框数线性）→ 文字多即超时；若识别结果置信度低（本场景常态），IoU 文字继承失效 → 每趟全量重识别 → 延迟钉死在高位。

**根源**：两阶段架构中 rec 成本无法压缩进 40ms 全帧预算。单框 40ms 里大部分是固定开销（裁剪、resize 到 48px 高、预处理、模型前向的常数项），不是算力不足，是**调用形态不对**。

### 3.2 移动识别不连续

**现象**：移动中框在动、文字闪烁/脱落，静止后才能"等"到识别结果。

**根源**：整条流水线是**分立识别**——det 线程（33ms 新鲜的框）与 rec 线程（100-500ms 前的文本）异步，文本靠 IoU>0.3 事后贴到框上。移动时新旧框重叠度低于阈值，文本立即脱落。**没有时间维度**：无 Kalman 滤波、无光流、无跨帧 ID，每一帧都是独立的世界。

### 3.3 分辨率与准确率

**根源是信息密度极不对称**：货架场景中 99% 的像素不含取件码，但通用全帧 OCR 对所有像素一视同仁。

- 640×480 写死（上游 `AImageReader_new(640, 480)`）：ROI 仅 286×640，标签 crop 十几像素高 → rec 输入 upscale 3 倍后的模糊图 → `23-6-1234` 读成 `1|110`。
- det target_size=320 进一步压缩可检测文字尺寸下限。
- 720p 只是线性缓解：手持距离翻倍 = 文字像素减半，仍然不够用。**全帧提分辨率是错误方向，正确方向是只对感兴趣区域投入像素（见路线 C）。**

### 3.4 硬件加速不适配

| 路径 | 实测/评估 | 结论 |
| :--- | :--- | :--- |
| GPU Vulkan | det 打平（28 vs 33ms），rec 劣化 4 倍；48px 高的小输入，GPU 显存分配/上传/派发固定开销 ≫ 计算量；着色器编译 19s/冷启动，ncnn 无持久化 pipeline cache | **否决** |
| NPU Hexagon | 只支持 SNPE/QNN/NNAPI 代理，ncnn 架构不支持；接入 = 换整套推理引擎 | **否决**（MVP 阶段） |
| CPU | det 33ms 已达 30fps 框率；rec 是唯一瓶颈 | **保留**，但需改变调用形态 |

### 3.5 已修复且对后续任何引擎都有效的工作（保留不回撤）

- 相机：默认后置、前后置切换、前置去镜像（`cv::flip`）
- 渲染：平台视图 VD→TLHC，25/30fps 稳定预览
- 交互：键盘不再顶起相机/底栏（`resizeToAvoidBottomInset: false`）
- 管线：删除防抖 sleep；智能 rec 调度（IoU 文字继承）；全链路性能埋点（`det_ms`/`rec_ms`/`nbox`/`text` → JSON + logcat）
- fork 改动全部记录在 `vendor/README.md`

## 四、可行解决方案

### 路线 A：掩码条件化字形检测（推荐主线）

**核心转变**：这是**检测任务，不是识别任务**。放弃"检测文字区域 → 识别语义"的两阶段 OCR 范式，也不设任何封闭字符集、不做字符级模板嵌入与几何装配：

> **输入 = 目标码的标准 mask（如用微软雅黑渲染的 `24-6-1234` 整串图像）× 场景图 → 输出 = 场景中相似字形图案的全部 box（有几个输出几个，没有就不输出）。**
>
> 模型从标准 mask 直接推理，学习的是**字形图案的通用形变不变性**——同一串字经扭曲、透视、缩放，甚至从微软雅黑换成宋体/彩云类字体，视觉上仍是"差不多的字形"。快递标签没有艺术字，这个甜区是稳定的。

这是特化的 OCR 检测器：**只检测期望检测的字形，场景中其余一切文字都是背景**。要找一个码就渲染一个码的 mask，模型本身永远不"读"字。

**为什么整串作为一个 mask 输入（而不是逐字符）**：

- 一次前向直接框出整串码，**没有字符切分、没有模板特征库、没有几何装配**——上一版设想的"逐字检测→共线拼装"整条后处理链全部消失。
- 整串的相对字形排列（字距、连字符位置）本身就是最强判别特征，比单字匹配抗误检几个数量级。
- 每帧成本 = 一次场景前向 + 一次 mask 条件化融合，与画面文字数量无关——彻底摆脱 rec 的 O(框数) 诅咒。

**模型结构**（全卷积，ncnn 可导出）：

- **场景骨干**：YOLO-nano 级骨干提取场景特征图，每帧一次前向。
- **mask 分支**：轻量卷积编码器，把查询 mask（定高、按需留白的整串渲染图）编码为条件特征；运行时可对任意输入码即时编码，**无离线模板、无预计算**。
- **融合与解码**：条件特征与场景特征图融合（SiamFC 式互相关或 FiLM 调制），检测头输出 box + 相似度分数。框的长宽比不由 mask 固定——透视/缩放形变由训练增广教会模型容忍。

**训练**：

- 数据可全合成：随机码渲染进货架/标签/纸箱背景，施加透视、缩放、模糊、光照、遮挡增广；**正样本场景字体 ≠ mask 字体**（微软雅黑 mask ↔ 宋体/黑体/打印体场景），强迫模型学习形状相似性而非字体记忆。
- **核心风险即核心训练点**：`23-5-1234` 与 `23-6-1234` 只差一个字形，相似度判别必须足够细——用**难负样本**（仅一位之差/仅连字符位置之差的码）做对比训练，把"一位不同"的响应差拉开。
- 纯负样本场景（无任何相似码）必须输出零 box，压制误检。

**推理流水线**：输入取件码 `24-6-1234` → 渲染标准 mask → 每帧一次前向 → 相似度分数超阈值的 box 即目标 → 高亮。匹配器从"字符串模糊匹配"退化为"取最高相似度 box"，逻辑大幅简化。

**风险**：单字之差的判别力（靠难负样本训练解决，需实测阈值分布）；过小字形仍依赖路线 C 的 ROI 放大兜底；极端透视（>60° 斜视）下的形变容忍需增广验证。

**模型与推理预算**（目标值）：

- **模型规模 ~10MB**：nano 级双分支（场景骨干 + mask 编码器 + 融合头）fp16 下足够——参照 YOLOv8n fp16 ≈6MB。容量不是本任务的风险项，难负样本的数据/损失设计才是。
- **推理预算：25fps 要求 ≤40ms/帧，目标 10ms**。10ms 全帧 CPU 推理是激进值，可达路径有三，按收益排序：
  1. **mask 特征按目标码缓存**——搜索会话期间 mask 不变，mask 分支只在用户输入/修改目标码时跑一次；每帧成本只剩场景骨干 + 融合头，接近普通 YOLO-nano 的三分之二。
  2. **两级推理（路线 C 落地形态）**：低分辨率（如 256）全帧粗筛 + 命中 ROI 后按原始分辨率精检，常帧成本压到粗筛一档。
  3. 输入分辨率收敛到 320-416 + fp16；此档输入下 YOLO-nano 级骨干在骁龙 7s Gen 2 CPU 实测区间约 20-40ms，配合前两条即可摸到 10ms 档。
- 反例警戒：PP-OCRv5 mobile det 仅 ~3MB 也吃了 33ms——模型小不等于快，**调用形态（每帧一次整图前向、无逐框串行、无 GPU 小输入派发）才是 10ms 的真正来源**。

### 路线 B：更小/更快的通用 OCR 模型

int8 量化、det target 160、裁剪版字典等。**方向错误**：当前瓶颈先在准确度（读错），不只是速度；更小模型只会让准确度更差。不值得独立投入，仅可作为路线 A 的辅助手段（量化自训模型）。

### 路线 C：场景特化 ROI——只计算模型感兴趣的像素（通用乘数，与 A 叠加）

**核心转变**：算力从 O(全帧) 降到 O(ROI)，等效分辨率提升 3-5 倍。

- 低分辨率全帧跑**极轻的粗筛**（经典 CV 即可：MSER/轮廓/长宽比/白底卡片检测，或 nano 级标签检测器），只把候选标签区域按原始分辨率裁剪送精识别。
- 同时解决速度（像素少）与准确度（等效放大）——这是"手持稍远也能识别"的唯一正解。
- UX 配合：**中心准星模式**——引导用户把手机对准单个货架层，默认只识别准星区域，扫码枪式交互，把"感兴趣像素"交给用户圈定，进一步压缩计算。

### 路线 D：连续性跟踪层（任何识别路线都必须补的课）

- 框级跨帧 ID：质心匹配 + Kalman 滤波速度外推，替代 IoU 硬阈值匹配。
- 文本绑定随 ID 传播：只有新 ID 或低置信 ID 才触发识别，其余帧直接继承。
- 移动中由预测器保持框位连续，识别结果异步追上也不丢目标。

### 组合建议

> **A（掩码条件化字形检测）+ C（ROI 特化）+ D（跟踪层）为目标路线**：A 解决架构性延迟与不连续，C 解决距离/分辨率物理约束，D 兜底移动连续性。B 不独立投入。

阶段验证指标（go/no-go）：

| 指标 | 门槛 |
| :--- | :--- |
| 单帧端到端（检测+分类） | ≤40ms（25fps） |
| 1m 距离标签首读正确率 | ≥95%（合成+实拍测试集） |
| 移动中（手持自然晃动）目标框连续性 | 框 ID 保持率 ≥90%，文本不脱落 |
| 冷启动到可扫描 | ≤2s |

## 五、代码现状

- `vendor/fast_paddle_ocr/` fork 全部改动保留（见 `vendor/README.md`），作为**备用/对照引擎**：UI 联调、回归对照、以及未来"对准即拍"单张高精度模式仍可使用其 `ocrFromImage` 路径。
- 性能埋点（`LuonnotarPerf`）保留，后续任何引擎接入都应复用同一套 det/rec/fps/text 观测口径。
- App 层（霜月 UI、匹配器、历史、相机管理）与引擎解耦，更换识别引擎只动 `lib/ocr/` 与原生层。
